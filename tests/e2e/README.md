# End-to-End Tests — Data Receiving

Orchestrates the full pipeline: sender → C# Data Receiving → Redis → RabbitMQ.

## Prerequisites

- C# service running on the target server
- RabbitMQ Management Plugin enabled (port 15672)
- Redis and Consul accessible
- `pip install -e ".[e2e]"` from the `sender/` root

## Run against the Wave 1 server

```bash
cd ~/desarrollos/sender
source .venv/bin/activate
python tests/e2e/run_e2e.py
```

## Run against a different server

```bash
DR_HOST=10.0.1.23 \
RABBITMQ_HOST=10.0.1.24 RABBITMQ_PASSWORD=<pw> \
REDIS_HOST=10.0.1.25 \
CONSUL_HOST=10.0.1.26 \
python tests/e2e/run_e2e.py
```

## Gate — Wave 2

T-01 through T-05 must all PASS (or SKIP) to advance to 2A4.
Results are saved to `tests/e2e/results/run_<timestamp>.json`.

### Fault tolerance test

**Run:** 2026-05-16  
**Method:** 300 frames sent at 5 frames/s through Nginx (port 5100); instance 02
stopped mid-traffic via `systemctl stop data-receiving-2`  
**Result:** ✓ 0 frame loss — all 300 frames received `ack=OK`

| Finding | Detail |
|---|---|
| Consul deregistration | Instance 02 called `Agent.ServiceDeregister` on graceful shutdown (logged at 23:43:57) |
| Frame loss | 0 — sender never saw a failed ACK |
| consul-template | Regenerates Nginx upstream automatically once Consul reflects the removal |

**Note on connection-level failover:** Nginx load balances at the TCP connection
level, not the frame level. The sender held a single persistent connection that
Nginx had routed to instance 01 before instance 02 was killed — so instance 02's
removal was invisible to that connection. In a real deployment each DTU sensor
has its own persistent connection; killing an instance mid-stream would trigger
the sender's exponential-backoff reconnect, which Nginx would route to a
surviving instance.
